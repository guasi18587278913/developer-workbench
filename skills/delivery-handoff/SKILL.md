# 开发、发布与故障记录

用能回查的事实说明当前状态，留下最小且足够接续的信息。

## 输入

- 任务目标和已确认范围。
- 代码版本或工作区、实际差异、检查结果。
- 若涉及发布或故障：实际运行记录、时间线、影响与恢复证据。

## 执行

1. 确认记录对象和截至时间。先看当前版本与差异，再按任务读取日志或既有记录，避免把旧周报中的“完成”当作当前状态。
2. 区分实现、合入、部署和用户链路验收。CI 成功只证明该批检查；进程启动或 HTTP 成功不能单独证明业务链路完成。记录不足时写“未知”或“未验证”。
3. 将实际命令、版本、结果和失败原因对应起来。同一操作的消息断线、超时或部分成功要保留未知边界，不据此自动重试有副作用的步骤。
4. 根据用途填写 [交接与复盘模板](assets/handoff.template.md)。普通交付保留结果、证据和下一步；故障再补触发条件、影响、原因、处置及回归验证。不要每次小改都生成长事故报告。
5. 对每个未完成事项写清卡点、现有证据和下一步最小动作。下一会话应能从记录定位现状，无需重新猜测仓库、分支或哪些步骤已执行。

## 写入与隐私

- 优先更新同一任务已有记录，不另造多个相互冲突的“最新状态”。用户指定文件或文档时写入该位置；外部分享遵循当前授权。
- 日志只保留解释结论所需的片段；移除密钥、令牌、个人数据与内部访问细节。公开版本使用通用示例，不上传完整生产日志。
- 只有真实执行过并读取结果的检查才能写成通过。记录中的建议与计划不能混入已完成事项。

## 交付

提供更新后的记录链接、主要结论和实际限制。若用户同时授权修复或其他工作，继续完成授权范围；若只请求复盘，不执行部署、回滚或付费探测。
