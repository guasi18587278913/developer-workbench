# 项目规则与 Skill

把已经验证的工作方式整理成 AI 能按需读取、按边界执行的项目规则。Harness 在这里指规则、工具、状态和验证共同组成的工作环境，不是额外的运行框架。

## 输入

- 目标仓库与用户希望改善的具体问题。
- 现有规则、启动入口、检查命令，以及一两个真实的成功或失败记录。
- 用户已确认的范围和授权；缺少信息时先从仓库定向查找。

## 执行

1. 读取适用的项目规则，以及与本次问题相关的 README、依赖清单和脚本。区分现有事实、用户偏好和待验证建议，不按模板把全库文档加载一遍。
2. 围绕实际摩擦确定修改：例如重复初始化、调错环境、规则冲突、完成状态不清。每条新规则说明它改变哪一个判断；删除同义重复和与当前项目无关的要求。
3. 长期共同约定留在项目规则；只在某类任务使用的流程才拆为 Skill。Skill 写清触发条件、输入、产物、必要步骤与停止条件。不得把每次修复的细节都升级为全局禁令。
4. 使用 [规则模板](assets/project-rules.template.md) 整理候选。仓库已有规则文件时就地合并，不并行新增第二套同义规则。只有用户要求两种客户端都支持时，才考虑维护两个入口，并说明如何避免冲突。
5. 用一个常规任务和一个边界任务走读规则：能否直接开始，能否找到相应检查，能否识别缺失的权限或证据。用户已授权实现时，完成可恢复的本地改动及必要验证；不要把每个阶段都变成再次确认。

## 输出

- 规则或 Skill 的具体差异。
- 每个入口适用的任务，以及移除重复内容的原因。
- 验证了哪些情形、仍需要真实项目观察哪些行为。

## 约束

- 规则不能扩大用户授权、覆盖上位项目规则或索取密钥。
- 启动、构建、测试和发布命令从目标项目确认；未确认的命令标为待查，不写成可直接执行。
- 发布、数据库、付费调用等沿用目标项目的授权边界。没有相关授权时先完成本地准备，不把 Skill 的存在当作执行许可。
- 若复杂方案确需独立复核，可参考 [方案压力测试提示词](https://github.com/guasi18587278913/developer-workbench/blob/main/prompts/solution-stress-test.md)，同时要求每个发现有实际依据，不为凑数量编造问题。
