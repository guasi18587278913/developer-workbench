# 规格与验收模板

将“想做什么”变成实现者和验收者都能依据的材料。复用已有项目结构；不重新实现或默认安装 Spec Kit。

## 输入

- 用户目标、实际使用者和要解决的场景。
- 当前实现、已有接口和需要保留的行为。
- 已确认的范围、时间与约束；不确定项保留为问题。

## 执行

1. 查找仓库现有规格和验收约定。已经使用 Spec Kit 时沿用其版本、目录、项目宪法和工作流；没有时使用 [功能规格模板](assets/feature.template.md)，不为一份文档新增工具链。
2. 把需求拆成可观察的行为。区分本次必须完成、明确排除、依赖他人和待确认的部分；重大产品选择不能当作已确认事实。
3. 将用户行为、数据归属、输入输出、失败表现和副作用写成契约。未知性能目标、费用或成功标准不得随意填数值。
4. 先检查已有模块能否满足需求，再写最小技术计划。新增依赖、表、进程或抽象须说明当前理由；明确验证和恢复方式。
5. 按可独立验收的结果拆任务。每项任务关联对应需求与验收用例，并注明前置依赖。文件列表只作定位，不能代替任务目标。
6. 对照需求、计划、任务、验收四者检查遗漏与冲突。优先解决影响实施的歧义，其余采用明确标注的可恢复假设。用户同时授权实施时继续完成已授权工作，不因阶段切换重复索要许可。

## 输出

- 规格、最小实现计划和可执行任务。
- 正常、边界、失败及副作用的验收条件。
- 已确认选择、必要假设、待决定事项和当前完成状态。

## 判断是否有用

另一个实现者能据此开始任务，另一个验收者能判断结果是否满足需求。文档存在、模板齐全或任务已勾选，都不能替代实际验证。
